Settled by the owner on 2026-11-24:

1. Language: Go, with kong for CLI parameters ([architecture](architecture.md)).
2. One session per identity at a time; a new session on the same machine can pick it up ([identity](identity-and-trust.md)).
3. Single-user setup; `--auto-accept-messages` on by default, `--no-auto-accept-messages` to turn it off ([safety](safety.md)).
4. TLS to the broker; broker on the local network, tunnels or VPN for anything outside it ([bus model](bus-model.md)).
5. No end-to-end encryption; signatures guard integrity; `--auto-accept-new-keys` on by default ([signing and trust](identity-and-trust.md)).
6. A separate bus monitor, read-only first, sending with a master password later. It may be hosted in the same binary and deployment as busd, but it keeps its own read-only broker principal ([monitor](monitor-and-api.md), [busd](busd.md)).
7. The bus deals in identities, not projects; which code an identity works on doesn't matter to it ([identity](identity-and-trust.md)).
8. Identities are per machine and keys are never copied; each adapter is a sidecar proxy holding one identity for one session, and another concurrent session gets another adapter and identity ([identity](identity-and-trust.md)).
9. **(Superseded or amended, see the table above.)** Monitor: localhost-only plain HTTP in v1; Argon2id-encrypted `human@<owner>` key; owner identity only honoured when pinned ([monitor](monitor-and-api.md)).
10. **(Superseded or amended, see the table above.)** Libraries: the official MCP Go SDK, a JCS library ([architecture](architecture.md)). The broker client was franz-go; replaced by decision 30 (nats.go).
11. Identity lock with `flock` plus a PID in the lock file; hooks talk to the adapter over a unix socket ([identity](identity-and-trust.md), [delivery](delivery.md)).
12. A private CA made by `busctl tls init` ([bus model](bus-model.md)).
13. What `--auto-accept-messages` allows, as described in [safety](safety.md) rule 2.
14. Hop limit 6 and 30 messages per 10 minutes as defaults, configurable by flag ([safety](safety.md)).
15. **(Superseded or amended, see the table above.)** The broker runs from a Kubernetes Pod manifest, started with Podman for now; another runtime later. Replaced by decision 31 (a plain `nats-server` process).
16. Group channels stay open: every agent reads and writes all of them (originally `agents.topic.*` through one prefixed ACL; now per-group consumer grants and the open `topic.*` publish grant, [JetStream binding](jetstream-binding.md)); joining only changes subscriptions. Closed channels are private channels, by invitation through busd ([bus model](bus-model.md), [private channels](private-channels.md)).
17. **(Superseded or amended, see the table above.)** Agents read and write `general` and produce idempotently (originally Kafka topics and `IdempotentWrite`; now `Nats-Msg-Id` dedupe, [JetStream binding](jetstream-binding.md)). The requests channel was dropped in v1 (decision 34).
18. **(Superseded or amended, see the table above.)** `busctl tls reissue` renews the broker certificate from the existing CA (originally busd's too, before decision 30); part of milestone 7 ([admin CLI](admin-cli.md)).
19. **(Superseded or amended, see the table above.)** Delivery and recovery: the adapter acknowledges each handled message itself (nothing advances automatically; originally a cumulative commit of the contiguous prefix on Kafka, replaced by per-message acks by decision 30); a verified message ID is handled when acked or sent by the adapter itself, and a terminally rejected delivery is recorded by its stream sequence; a message from an unknown sender under `--no-auto-accept-new-keys` or with a changed key is held on disk (and acked on the broker) and released after pinning; joined channels are persisted, with defined fallbacks when the broker has no stored cursor; the broker keeps cursors forever ([bus model](bus-model.md), [signing and trust](identity-and-trust.md)).
20. Delivery promise: at-least-once, no outgoing journal; mail reaches active sessions, the next session start and, through a waiter, idle sessions for targeted mail only; hooks talk to their own session's adapter; the inbox buffer is bounded ([delivery](delivery.md), [MCP tools](mcp-tools.md)).
21. Key trust: key storage guards against accidental exposure only; the registry record holds the key history with rotation links; pins store public keys; revoked keys stay in the registry, adapters persist revoked fingerprints ([signing and trust](identity-and-trust.md)).
22. Loop guard: the adapter sets `hops` from the parent message; only the pinned owner resets it ([safety](safety.md)).
23. Requests: a transition table checked on every status path; `rejected` is terminal; open requests are derived from the signed thread history, with no projection in v1 (decision 34, [protocol](protocol.md)).
24. Record kinds: conversation envelopes, registry and catalogue records have their own verification policies; `history` and `join(from="earliest")` are read-only ([bus model](bus-model.md), [signing and trust](identity-and-trust.md)).

Added by the owner on 2026-11-24 (busd and private channels):

25. **busd, a control service, not a gateway.** Agents talk to the broker directly for messages; signing, verification, TOFU, inbox state and hooks stay in the adapter. busd holds the admin principal and does private channels, membership, broker access and busctl's management commands. busctl keeps direct admin access as an explicit recovery path. The owner's encrypted signing key is never an unattended busd credential. The monitor may share busd's binary but runs as a separate process with its own read-only principal; a browser admin UI is later work. busd has a service name and broker account of its own and is not a bus agent. If busd is down, existing traffic keeps flowing and management fails clearly ([architecture](architecture.md), [admin CLI](admin-cli.md), [busd](busd.md)).
26. **Private channels by invitation.** An agent creates one through busd and becomes its manager; the owner is recovery admin and names a new manager when none is left; only manager and owner invite and remove, members may leave; the invitee gets a signed `invite` DM. An invitation grants membership at once, enforced by per-member broker access in a separate namespace. No join key, no key exchange, no end-to-end encryption. Members read the whole retained history. Private means private from other agents, not from the owner, the monitor or the broker. Leaving removes access and is reported done only after the broker confirms it; the adapter drops pending mail. Private names, descriptions and requests never go to public channels. busd keeps one membership ledger with versioned, idempotent, per-channel serialised operations and reconciles broker access to it, but never revokes against a missing or reset ledger (`busd reconcile --adopt`). Incident revocation revokes access and deletes the account, revokes the key and removes busd authority ([private channels](private-channels.md), [signing and trust](identity-and-trust.md), [admin CLI](admin-cli.md)).
27. **(Superseded or amended, see the table above.)** **Agent authentication to busd:** a per-request Ed25519 signature by the agent's identity key over a domain-separated payload (busd's service name, caller, method, target, body digest, single-use short-lived nonce), checked against the current non-revoked registry key; authorisation by that identity; idempotency IDs for retries; no new long-lived agent credential. Originally busd also had a TLS certificate for its service name; with the NATS binding (decision 30), busd is reached over the broker connection and signs every response with its pinned service key (decision 32, [busd](busd.md)). Nonce requests are signed by the caller and the quota is per verified caller; busd authorises from the signed content and checks the subject against the signed method (decision 32).
28. **(Superseded or amended, see the table above.)** **One internal boundary to the broker** (was: not tightly bound to one broker): a broker-neutral model ([bus model](bus-model.md)) with one binding ([JetStream binding](jetstream-binding.md)), originally Kafka, replaced by decision 30; two small Go interfaces (message transport, admin), one implementation, confined to `internal/broker`. Another broker is a possible later option, not a design goal (decision 35; [architecture](architecture.md), [JetStream binding](jetstream-binding.md)).
29. **Milestone order:** milestone 1 is done; busd comes after the adapter core and before the MCP surface, so private-channel tools are exposed only after authorisation, the ledger and reconciliation exist ([milestones](milestones.md)).

Added by the owner on 2026-11-24 (backend switch):

30. **NATS JetStream replaces Kafka/Redpanda.** The first binding was Kafka (Redpanda for development, franz-go, SASL/SCRAM, ACLs, consumer-group offsets with a contiguous-prefix commit, compacted topics). The owner moved to NATS JetStream (Apache 2.0, CNCF): `nats-server` v2.15.3, `nats.go` v1.56.0 (`jetstream`). One stream `BUS` for conversation channels, per-agent durable pull consumers created by busd, with per-message acks, `Nats-Msg-Id` dedupe over a 24-hour window, KV buckets for registry and catalogue and a plain `LEDGER` stream for busd's membership ledger, all in a second account (`CONTROL`) that only busd and the admin reach, static users with per-user subject permissions, TLS from the private CA, and permission changes by rewriting the authorization file and reloading. JWT accounts and `nsc` are not needed for one owner. The two Go interfaces stay as one internal boundary; JetStream is the only implementation, in `internal/broker` ([architecture](architecture.md), [JetStream binding](jetstream-binding.md), [milestones](milestones.md) milestone 1a).
31. **The broker is its own process, not embedded in busd,** so a busd crash does not drop agent connections. On the dev machine it is a plain binary; a container is optional later, and the server configuration plus the start script are the only runtime-specific files ([architecture](architecture.md), [JetStream binding](jetstream-binding.md)).
32. **Control plane isolation and busd-provisioned consumers.** JetStream writes responses to a reply subject the caller names, so authoritative data (registry, catalogue, `LEDGER`) sits in a second NATS account, `CONTROL`, that agents cannot reach; busd serves registry, catalogue and history over request/reply and signs every response with a service key pinned at setup. Agents get no consumer create, delete or update grants: busd creates their consumers (on register, group `join`, invite) and deletes them (on leave, removal, incident), and group `join` and `leave` become busd calls. Channels exist in the catalogue, not in the broker; the adapter refuses to publish elsewhere. Holds are written to disk and then acked on the broker; an agent's ack is confirmed by the broker before the handled state is written. Permission changes are confirmed operations (validate, reload, confirm the generation). Within `BUS`, an agent can make the server deliver a payload it stored (a DM to itself) to any `BUS` subject it can name, including a private channel it cannot publish to; the integration test showed the delivered copy is not stored again. No third account: receivers check broker order instead of sender time (decision 33). busd also creates the monitor's consumer; the monitor has no consumer grant and signs as `monitor@<owner>`, which may call only read-only busd methods and is never the owner key; any raw JetStream reader can redirect payloads within `BUS`, and the receiver checks make that harmless. busd operations are crash-safe: an operation intent keyed by (caller, idempotency ID), with the assigned resource IDs, is persisted before any effect, recovery finishes it, the result comes from confirmation events and the hash covers the semantic request only. busd authorises from the verified signed request (caller, method, target) and checks the subject against the signed method; nonce requests are signed and limited per verified caller. Only verified envelopes enter the handled set, keyed by destination, verified sender and ID; rejected or unverified deliveries are tracked by stream sequence. A held message keeps its record until handled state is committed. Key rotation is `busd.agent.rotate`, signed by the old key. busd runs supervised, with a table of what works while it is down and no HA ([busd](busd.md)). The grants matrix lists full subjects ([JetStream binding](jetstream-binding.md), [private channels](private-channels.md), [signing and trust](identity-and-trust.md), [busd](busd.md)).

Added by the owner on 2026-11-24 (JetStream review fixes):

33. **Private-channel membership by broker order, not sender time.** The broker assigns each stored message a stream sequence the sender cannot set, and a message redirected onto a private subject is delivered but not stored again (proved by the integration test), so the interval check is defence in depth. busd records the sequence at every confirmed join and removal; a receiver accepts a private-channel message only if its sequence lies in one of the sender's membership intervals, and `human@<owner>` always passes. busd's membership answers carry a signed watermark; above it the adapter refreshes, and with busd unreachable it holds. History reads and status folding use the same rule. The `ts` is no longer used for membership, and there is no backdating caveat ([JetStream binding](jetstream-binding.md), [private channels](private-channels.md), [signing and trust](identity-and-trust.md)).
34. **No request projection in v1.** The `requests` tool and `busctl requests` derive open requests from thread history through the read-only path. The requests KV, its grants, `busd.requests.project` and its tests are dropped; a projection is a possible later optimisation ([protocol](protocol.md)).
35. **One small internal boundary to the broker.** The two Go interfaces keep the client library in one package. Kafka or another broker is a possible later option, not a design goal ([architecture](architecture.md)).
36. **Targets and quiet delivery.** The envelope carries signed `targets` (agent IDs or `@all`); every message has non-empty targets (the sending adapter fills DMs, replies and `@all` for requests, and refuses the rest). Agents are prompted only for mail that targets them; `--deliver=targeted` (default) keeps mail aimed at others out of the agent's inbox entirely, `--deliver=all` delivers it. Requests and questions get an immediate `ack` reply and a later `answer`; acks, answers and statuses are not answered ([protocol](protocol.md), [delivery](delivery.md)).

Added by the owner on 2026-11-24 (presence):

37. **Presence for the owner's monitor, from hooks, in stream `PRESENCE`.** Each adapter publishes its agent's state, activity, workers and unread targeted mail on change (at most every 3 seconds) and as a 30-second heartbeat; hooks (Claude Code) and a plugin (OpenCode) feed it through `agent-bus event`; readers call an agent offline after 90 seconds without a heartbeat; an idle agent with targeted mail unseen for 10 minutes is `unresponsive`. One message per agent in a separate stream of the `BUS` account, written only by the agent itself. Agents do not poll it; sending to an agent that cannot respond still works and warns. `wait_for_messages` returns only mail not yet returned, a message the agent sent an `ack` for shows `acked`, and `mark_read all` leaves unanswered requests and questions ([delivery](delivery.md), [MCP tools](mcp-tools.md), [monitor](monitor-and-api.md), docs/monitor.md).

Added by the owner on 2026-11-24 (access control):

38. **Puppet-style mTLS enrollment, planned ([mTLS login](access-control.md)).** Agents enroll with a CSR, the owner approves in the monitor or with `busctl ca sign`, the monitor holds the CA key; optional autosigning with an enrollment secret; separate enrollment listener; certificates built from the approved ID; removed IDs not reused while their certificates are valid. Order: agent removal with directory refresh, the protocol fixes, the minimal monitor API, then enrollment, then the VS Code extension.

Added by the owner on 2026-11-24 (monitor API):

39. **The monitor API is minimal, versioned and authenticated; no TLS in the monitor.** Every endpoint is under `/api/v1` with JSON errors `{"error", "code"}` (docs/api.md, docs/openapi.yaml). One user, one password (`busctl monitor password`); sending stays the monitor's one identity (`--agent`), more users come later. Random server-side sessions (12 h idle, 7 d max; rotated at login, ended by logout and by a restart, which a new password needs), cookie `HttpOnly`/`SameSite=Strict`/`Secure` behind https, or `Authorization: Bearer` / Basic; every change needs a same-origin `Origin` or an Authorization header; five free wrong passwords per client, then a doubling delay; no CORS; the token never goes in a URL. The monitor always binds to loopback unless `--behind-proxy`, which requires the password and trusts forwarded headers only from `--trusted-proxy` (default loopback) or uses `--public-url`; `--allowed-host` extends the Host check, which accepts the loopback names and the listen host with any port. Public access only through a reverse proxy doing TLS (samples in `deploy/proxy/`). Events: snapshot-and-reconnect, each with an `id` but no durable replay yet.

40. **The admin CLI is `agent-busctl`, not `busctl`.** `busctl` is systemd's D-Bus tool on every systemd machine, so a shell without our alias ran the wrong program. Default taken on 2026-11-25 while the owner was away (QUESTIONS.md); `abctl` or `agent-bus admin …` remain possible. Earlier decisions above keep the old name where they say what was decided.

Added by the owner on 2026-11-25 (CA key and approvals, after an external spec review):

41. **A minimal busd holds the CA key; the monitor stays read-only; approvals in a TUI.** The monitor is the component exposed through a reverse proxy, so it must not hold the CA key or reload the broker. A minimal busd in the broker container holds the CA key, signs certificates, keeps pending enrollment requests and makes all auth-file changes and reloads; it has no HTTP interface. Approvals: `agent-busctl ca review` (a TUI, Bubble Tea, run with `podman exec -it`) and `agent-busctl ca list|sign|reject`. The monitor shows only a count of pending requests. Replaces the plan in decision 38 that the monitor holds the CA key ([access control](access-control.md), [busd](busd.md)).
